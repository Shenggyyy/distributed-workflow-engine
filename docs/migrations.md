# Database migrations

M0.7b introduced Alembic with an empty `0001` baseline. M1.2 adds revision
`0002`, containing workflow identities and append-only JSONB definition versions.
See [workflow storage](workflow-storage.md) for the tables and mutation guard.
M1.6 adds revision `0003` with run, task and attempt tables, lifecycle guards
and history protection. See [runtime storage](runtime-storage.md).
M1.8a adds revision `0004` for [run-creation request bindings](run-idempotency.md).

## Execute migrations explicitly

Run from the repository root after installing locked dependencies. For the local
Docker database published on port 15432:

```powershell
$env:DWE_POSTGRES_PUBLISHED_PORT = "15432"
docker compose up -d --wait --wait-timeout 120 postgres

$env:DWE_DATABASE_PORT = "15432"
$env:DWE_DATABASE_PASSWORD_FILE = "secrets/postgres_password.txt"

uv run --locked alembic heads
uv run --locked alembic upgrade head
uv run --locked alembic current
uv run --locked alembic check
```

`heads` lists the repository head; `current` reads the connected database's
revision. Both should show `0004 (head)` after upgrading to the current head.
Repeated `upgrade head` applies no revisions once current.
`check` compares the migrated schema to the shared SQLAlchemy metadata and
fails when a new autogenerated change would be needed. It is not a full proof
of schema equivalence.

Settings and credentials follow the existing [database configuration](database.md).
To select an explicit dotenv file:

```console
uv run --locked alembic -x env_file=.env.database-test upgrade head
uv run --locked alembic -x env_file=.env.database-test current
uv run --locked alembic -x env_file=.env.database-test check
```

Use `-c <absolute-path-to-alembic.ini>` when invoking Alembic from a different
working directory. Password-file paths still resolve against the working
directory. There is no database URL or credential in `alembic.ini`.

Neither the API nor `engine check-db` runs migrations automatically.
`check-db` proves connectivity only; it can succeed on a database without
`alembic_version`. API liveness also remains independent of migrations.

## SQL review without a database

```console
uv run --locked alembic upgrade head --sql
```

Offline generation does not load application settings, read passwords, or connect.
It emits SQL for a PostgreSQL target, including transaction boundaries. It does
not inspect the database's current revision and does not acquire the online
migration lock. Do not apply offline SQL concurrently with online migrations;
its execution and coordination are the operator's responsibility.

## Transactions and concurrent execution

Online commands reuse the application's SQLAlchemy engine and open one outer
transaction. Before accessing migration state, they attempt the database-scoped,
transaction-scoped advisory lock `0x4457454D4947`. A competing command fails
immediately with a clear message, rather than running concurrent DDL.
All online environment commands, including `current` and `check`, take this lock.
It is released when the outer transaction commits or rolls back, including on
connection termination.

Ordinary PostgreSQL transactional DDL and Alembic version changes commit together.
A failed revision rolls them back together. No automatic replay occurs, and a
connection loss during COMMIT can leave the result unknown. Reconnect and inspect
the revision and actual schema before deciding how to recover.

The lock only coordinates commands that use this environment. It does not stop
manual DDL or another tool that ignores the lock. Normal PostgreSQL DDL locks can
still block application traffic. Existing connection/pool/statement timeout
settings apply; review and adjust them deliberately for a long migration.

Migration scripts must preserve the outer transaction: do not call commit,
rollback, or Alembic autocommit blocks. Operations such as
`CREATE INDEX CONCURRENTLY` need a separately designed execution protocol
because they cannot run inside this transaction. They are outside this baseline.

For programmatic tests/tools, `Config.attributes["connection"]` can supply an
already-open SQLAlchemy connection with an active transaction. The caller owns
commit/rollback; exceptions must escape that transaction's context.
Commands without an injected connection own their engine and transaction.

Configuration errors and SQLAlchemy failures produce fixed Alembic CLI errors
without printing driver messages or credentials. The database exception class is
included for diagnosis. Do not enable raw SQL logging with secrets in statements.

## Revision authoring and packaging

The environment, revision template, and revision files live under
`src/workflow_engine/migrations/` and are shipped in the wheel.
`alembic.ini` uses the package resource `workflow_engine:migrations` rather than
a working-directory-dependent source path. The Docker runtime also contains the
configuration file and Alembic, so it can be used for an explicit migration job.
The API container reads its mounted database secret for workflow storage and
explicit migration commands.

The shared `schema.py` metadata describes workflow definitions and runtime tables.
It defines predictable names for primary keys, indexes, unique constraints,
foreign keys, and checks. Trigger/function DDL is recorded separately in the
migration and verified by integration tests.
Check constraints require an explicit descriptive name. Import all future table
definitions into this metadata before using autogenerate.

In an editable development checkout, generate a candidate after changing metadata:

```console
uv run --locked alembic revision --autogenerate -m "describe schema change"
uv run --locked ruff check src/workflow_engine/migrations --fix
uv run --locked ruff format src/workflow_engine/migrations
```

Review the generated upgrade and downgrade code before running it. Autogenerate
does not reliably infer every change, especially renames and data transformations.
Keep one revision head and never rewrite a revision already shared or applied.
Create a new revision instead. Do not generate revisions inside a deployed image.

See [Alembic autogenerate guidance](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)
and [programmatic connection sharing](https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands).

## Downgrades and verification

Downgrading from `0004` to `0003` removes all request bindings while keeping runs.
This loses deduplication history; re-upgrade cannot reconstruct it.
Downgrading from `0003` to `0002` deletes all run/task/attempt data while preserving
published definitions. Downgrading from `0002` to `0001` also drops workflow/version
tables and their data. Downgrading further to `base` removes the version row;
Alembic may retain the empty version table. A subsequent `upgrade head` recreates
missing tables at `0004`; it does not restore deleted records. Review every
downgrade's data loss implications; downgrade is not an automatic recovery strategy.
Never use `stamp head` as a substitute for applying missing schema changes.

Migration integration tests use generated private schemas in the explicitly
configured test database. They create/drop only their own schemas and cover:

- Fresh upgrade, repeated upgrade, downgrade, and re-upgrade.
- Schema/metadata comparison.
- Injected failing DDL: schema change and revision number roll back together.
- Concurrent migration rejection and lock release.
- Unknown database revisions being rejected without overwriting version state.

Run with the same configuration used for database integration tests:

```console
uv run --locked pytest tests/integration --database-env-file .env.database-test
```

The account needs permission to create schemas in this test database. The fixture
drops its generated schema with CASCADE during cleanup; interrupted processes can
leave a test schema behind. Use a disposable database.

CI runs the real migration tests, then executes the CLI upgrade/current/check
sequence against its disposable Compose database at the current head. It also verifies that the
runtime image contains the revision and template. Ordinary pytest runs skip
infrastructure tests unless `--database-env-file` is provided.
