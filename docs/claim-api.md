# Task claim HTTP API

M2.2d.2a exposes the [idempotent claim repository](idempotent-claims.md) over HTTP.
It uses schema `0007` without a new migration. OpenAPI is at `/openapi.json`, with
interactive documentation at `/docs`. Lease renewal HTTP remains M2.2d.2b.

## Request and response

`POST /worker-sessions/{session_id}/claims` requires a JSON object:

```json
{
  "run_id": "f7023352-aabe-4a7b-86bb-cce2c47b8ad8",
  "request_id": "97979d72-35a6-496c-b072-fee6e3b80462"
}
```

The example UUIDs illustrate shape only; use a real Run and registered Worker
session. The request UUID is generated by the Worker before a new poll and kept
across uncertain retries. Identity is `(session_id, request_id)`, bound to one
Run. UUID text follows the existing API's UUID parsing rules; equivalent spellings
refer to the same database UUID. Unknown fields, including client lease duration,
timestamps, lease_token or a second Worker identity, return 422.

`Idempotency-Key` is rejected with 400, including empty or duplicate headers.
Run creation uses that header, whereas this endpoint uses its required request_id
field. Supplying a header does not replace a missing body field.

New allocations, valid replays and no-work results all return **200**. The required
response fields are worker_session_id, run_id, request_id, and claim:

| claim | Meaning |
| --- | --- |
| null | This poll committed a no-work result, or replays that retained result. |
| Object | The committed allocation's current valid ownership and pinned Task definition. |

The claim object contains workflow_version_id, task (`TaskRun`), attempt
(`TaskAttempt`), lease (`AttemptLease`), and definition (`TaskDefinition`). Task
and Attempt are RUNNING. The lease includes attempt_id, worker_session_id,
lease_token, acquired_at, last_renewed_at and lease_expires_at. UUIDs are strings;
timestamps include a timezone. The token is returned so the eventual Worker can
present its ownership on renewal/completion. It is not printed by the smoke script
or included in the response model's repr.

Successful responses set `Cache-Control: no-store` and no Location header. There
is no claim query endpoint or HTTP renewal/completion endpoint in this commit.
Errors use the existing error envelope and never include a claim/token.

## Transaction, replay and delivery semantics

The synchronous handler runs in FastAPI's thread pool. It creates one fresh
transaction, invokes the keyed repository, validates the full response model, then
exits the transaction before returning success. INSERT errors, response-model
validation errors and deferred COMMIT failures therefore cannot return a successful
grant or retain a partial allocation. Storage-error logging retains exception types
and stack frames without bound values, exception messages or tokens.

A client disconnect after COMMIT can still lose the response. Retrying the same
session/request/Run retrieves the original retained decision. Do not automatically
generate another key for an uncertain outcome: that would be a new allocation.
The endpoint does not itself retry requests or transactions.

No-work stays null after capacity frees or tasks become READY. Use a new request
ID for the next actual poll. A bound live Attempt may replay even when the Worker
heartbeat expired or its session is LOST; those conditions still block new claims.
Replay may return a later lease snapshot after an independent renewal. It never
extends the lease, reactivates the Worker or allocates a replacement Attempt.

Expired or terminal ownership returns `409 claim_replay_unavailable`, not null.
Changing run_id under an existing identity returns `409 claim_request_conflict`,
even when the original allocation is no longer available. Repository state, clock,
capacity and lock ordering remain as documented in [idempotent claims](idempotent-claims.md).

The database verifies lease validity at its locked clock observation, not at client
receipt time. Delayed responses may already be expired. The future execution loop
must honor ownership and avoid launching a second local handler for a replayed
Attempt. Request deduplication is not exactly-once execution or business-effect
idempotency. This endpoint reserves capacity; it does not execute handlers, resolve
dependencies, recover expired Attempts or release their slots.

## Server configuration and access boundary

`DWE_ATTEMPT_LEASE_SECONDS` sets new HTTP claim lease duration, default 30 seconds,
range 1–86400. It is loaded in the immutable Settings snapshot at process startup,
and Compose forwards it into the API container. Changing the environment of an
already running process does not change that snapshot. Replay ignores the new-claim
duration and uses persisted lease metadata.

This setting is independent of `DWE_WORKER_HEARTBEAT_TIMEOUT_SECONDS`, heartbeat
send intervals, renewal intervals and the future task execution timeout. The
Python repositories/examples retain their explicit constructor policies; this
HTTP setting does not silently change those calls.

The API retains the project's trusted local development boundary. There is no
authentication or per-session access control yet: someone who can call the API can
submit requests for a known session. UUIDs are identifiers, not credentials. Keep
the local binding used by Compose; authenticated session ownership and TLS are
required before exposing grants outside that boundary. The endpoint does not
provide a production Worker security model.

## Error mapping

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | idempotency_not_supported | Idempotency-Key was supplied. |
| 404 | run_not_found / worker_not_found | New claim references a missing parent. |
| 409 | run_inactive / worker_inactive | New claim admission is closed. |
| 409 | worker_expired | New claim's Worker heartbeat expired. |
| 409 | claim_request_conflict | Request identity is bound to another Run. |
| 409 | claim_replay_unavailable | Bound execution is expired, terminal or owned by a STOPPED Worker. |
| 409 | attempt_number_exhausted | Task's next Attempt would exceed the integer limit. |
| 422 | invalid_request | Invalid path, body or field. |
| 500 | storage_error | Invalid persisted relationships/schema or other storage invariant failure. |
| 503 | database_not_configured / database_unavailable | Missing database configuration, connection/pool/SQL/lock timeout or similar operational failure. |
| 503 | worker_clock_regression / lease_clock_regression | Database observation precedes the relevant accepted timestamp. |

The error envelope is `{ "error": { "code": "...", "message": "...", "details": [] } }`.
Validation details contain field locations and error types, not input values.
Conflict, unavailable execution and clock regression remain distinct decisions;
an error does not permit the caller to reuse an old grant or change request input.

## Local example and tests

Rebuild/start the API with the existing local port/secret configuration and apply
`alembic upgrade head` if necessary. Then run these together so Worker registration
is followed promptly by the claim:

```powershell
$baseUrl = "http://127.0.0.1:8000"
$definition = Get-Content examples/diamond.json -Raw
$version = Invoke-RestMethod -Method Post -Uri "$baseUrl/workflows" -ContentType "application/json" -Body $definition
$runBody = @{ workflow_version_id = $version.id } | ConvertTo-Json
$run = Invoke-RestMethod -Method Post -Uri "$baseUrl/runs" -ContentType "application/json" -Headers @{ "Idempotency-Key" = [guid]::NewGuid().ToString() } -Body $runBody
$sessionId = [guid]::NewGuid().ToString()
$workerBody = @{ worker_name = "claim-http-demo"; max_concurrency = 2 } | ConvertTo-Json
Invoke-RestMethod -Method Put -Uri "$baseUrl/worker-sessions/$sessionId" -ContentType "application/json" -Body $workerBody | Out-Null
$requestId = [guid]::NewGuid().ToString()
$claimBody = @{ run_id = $run.run_id; request_id = $requestId } | ConvertTo-Json
$uri = "$baseUrl/worker-sessions/$sessionId/claims"
$first = Invoke-RestMethod -Method Post -Uri $uri -ContentType "application/json" -Body $claimBody
$replay = Invoke-RestMethod -Method Post -Uri $uri -ContentType "application/json" -Body $claimBody
$first.claim.attempt.id -eq $replay.claim.attempt.id
```

Expect `True`. Tokens remain inside the response variables. This disposable Run
retains one RUNNING Attempt; automatic completion/recovery is not available yet.

```console
uv run --locked pytest tests/test_claim_api.py
uv run --locked pytest tests/integration/test_claim_http.py --database-env-file .env.database-test
uv run --locked python scripts/check_claim_api.py
```

The smoke script supports `--base-url` and runs in container CI after migrations.
Each invocation creates a Workflow version, Run and Worker, claims Task A, replays
it, verifies no-work replay and checks 409/404/422/400 errors. It prints no grant
payload and requires a disposable test environment for repeated runs. Database
tests additionally cover deferred commit and response validation rollback, current
renewal, terminal/expired grants, concurrent conflicts, sanitized storage errors,
lock timeouts and liveness during a blocked request.
