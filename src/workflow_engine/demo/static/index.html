01 / SUBMIT

提交工作流

API 保存定义与 Run；以下为已提交的数据。演示使用可信定时 Handler，执行内容包括等待与真实采样；不生成业务报告，DAG 边不自动传递任务数据。

02 / DEPENDENCIES
先看依赖，才知道谁可以执行

      
箭头向下表示真实 depends_on。同一层允许并行；只有所有直接依赖 SUCCEEDED，后续任务才具备就绪条件。

      

      
状态来自 PostgreSQL · READY 可领取 · RUNNING 已分配 · PENDING 等待 · RETRY_WAIT 等重试

    

    

      
03 / POSTGRESQL READY VIEW
当前哪些任务可领取？

      
这是 PostgreSQL 中 Task 状态的视图，不是另一个消息队列。Scheduler 更新依赖与就绪状态；Worker 再来申请领取。

      
READY · 可申请领取
仍需等待

      
以下原因由同一个数据库快照推导，是当前条件，不是 READY 转换事件历史；短暂状态可能落在两次轮询之间。

    

    

      
04 / WORKER PULL
Worker 有空位，就申请领取

      
Worker pull → 引擎事务校验容量与 READY 状态 → 创建 Attempt 和 Lease → Worker 执行 Handler。

      
这是协议说明，不是网络消息动画。卡片展示已确认的领取结果；任务归属由领取事务决定，未预先分配给指定 Worker。

      

      
槽位显示配置容量和数据库中的 RUNNING 归属数量，不代表可观测的物理槽位编号。心跳新鲜度不等于连接探测；Run 结束后 Worker 正常退出，随后心跳过期本身不说明任务失败。

    

    

      
05 / RECONCILE & RETRY
结果返回，开始下一轮调度

      
成功 → 依赖满足 → 调度为 READY↺ 回到 03 可领取失效且允许重试 → RETRY_WAIT → 到期后 READY → 新 Attempt↺ 回到 04 Worker pull

      
回路表示引擎规则；下方才是本 Run 已保存的证据。成功回报不会让页面自行修改下游状态。

      

      

      
恢复判断：心跳截止用于判断 Worker 会话失联；Attempt 的 Lease 到期由引擎恢复事务确认。Lease 到期不是 Handler 结束时间。新 Attempt 从头执行，不是旧 Worker 转交，也不是断点续跑。

      
演示脚本在 fail 命令中启动替代 Worker B；这不是自动扩容。页面没有 Docker 停止事件，不能仅凭心跳过期证明发生了 SIGKILL。终端输出保留故障注入动作。
